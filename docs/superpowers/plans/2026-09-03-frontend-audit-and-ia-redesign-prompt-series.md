# Run the frontend audit and IA redesign as Claude Code and Claude Design prompts

This page turns the frontend contracts (`DESIGN.md`, `.impeccable.md`, `PRODUCT.md`, `CONTEXT.md`, `caos/frontend/docs/control-capability-map.md`), the approved production design plan (`CAOS-PRODUCTION-DESIGN-PLAN-2026-08-31.md`), the last critique (`IMPECCABLE-CRITIQUE-2026-08-31.md`), and the UX and WEB check families of `ENTERPRISE_TESTING_READINESS.md` into three assessment prompts, two Claude Design briefs, four goal prompts for Claude Fable 5.1, and three recurring loop prompts for Claude Opus 5. It tells you the order to run them, which checkout each one runs in, which model and effort to use, where Claude Design enters and what its output is allowed to decide, and what you must decide between prompts. The prompts follow the same guidance as the enterprise series (`docs/superpowers/plans/2026-09-02-enterprise-readiness-prompt-series.md`): a goal, the reason behind it, binding constraints, and a definition of done, rather than a step list. They reuse that page's standing preamble by pointer and add a frontend addendum.

The series is deliberately separate from the enterprise-readiness series. Enterprise Tasks 12 and 13 are still pending, Task 12b (`ER-G8`) rewrites the browser journey for three browsers, and an IA change moves every route the browser gates pin. Decision D5 below says how the two series interleave.

## How to run the series

### Models and effort

Use `claude-fable-5-1` for every assessment (`FE-A0` to `FE-A2`), every Claude Design brief (`FE-D1`, `FE-D2`) and every goal prompt (`FE-G1` to `FE-G4`); use `claude-opus-5` for the loops (`FE-L1` to `FE-L3`). Switch with `/model claude-fable-5-1` or `/model claude-opus-5` at the start of the session. Fable 5.1 holds a whole audit or a whole IA change in one turn, and the design briefs need its craft; a loop tick is a fixed command sequence plus a diff against the last log entry.

Keep the default effort (`xhigh`) for assessments, design briefs and goals. Drop loops to `medium` if your build exposes the control.

The design briefs are the exception to the autonomy rule: you are in the room. `FE-D1` stops for you to pick a direction and `FE-D2` stops for you to approve the screens, so run them when you can look at the canvas within the hour; everything else runs unattended.

### Where each prompt runs

Every prompt runs in a git worktree under `.claude/worktrees/`, never in the primary checkout, and one session owns a worktree at a time.

- **`FE-A0`, `FE-A1`, `FE-A2`** (assessments): three detached worktrees from `main`, one each, so the three audits run in parallel. Create each with `git worktree add --detach .claude/worktrees/fe-audit-<code|ia|design> main`, then inside it run `npm ci` in `caos/frontend` and, for `FE-A0` only, build the interpreter (`uv run --project caos/server --extra dev python -m pytest --version`, then `git clean -f caos/server/uv.lock`) and start a host-control app on its own port so the browser gates can run: `CAOS_PROVIDER=host_control PORT=8766 CAOS_DATA_DIR=.dev-data-audit python caos/server/dev.py` beside `python caos/server/worker.py`, and `CAOS_URL=http://127.0.0.1:8766` for the scripts. No assessment edits source; each writes only its report and scratch files.
- **`FE-D1` and `FE-D2`** (Claude Design): one worktree on its own branch, `git worktree add .claude/worktrees/fe-design -b claude/fe-design-directions main`, because both briefs commit the artboard working files there. They write only under `docs/design/canvas/` (the artboard working files) and `.superpowers/sdd/frontend/` (the report), and they publish a canvas through the Artifact tool. They need a session with the `/design` skill and the Artifact tool, which the Claude Code web and desktop sessions provide; that branch lands through its own pull request once `FE-D2` is approved.
- **`FE-G1` to `FE-G4`** (goals): a fresh worktree each, branched from `main` after the previous pull request merges: `git worktree add .claude/worktrees/fe-task-02-ia-shell -b claude/fe-task-02-ia-shell main`, then enter it. Each task lands through its own pull request. The browser gates run against the combined app on `:8000` (`python caos/server/dev.py` with `CAOS_PROVIDER=host_control` and `python caos/server/worker.py`), or on a second port with `CAOS_URL` set, exactly as the Task 8 and Task 9 reports did.
- **`FE-L1`** (frontend branch health): a detached verify worktree that no goal session edits, `git worktree add --detach .claude/worktrees/verify-frontend main`, with `npm ci`, the interpreter, and a host-control app on `:8767` so the loop can run the browser gates without touching `:8000`.
- **`FE-L2`** (pull-request babysit): the worktree that owns the branch under review, only while no goal session is active there.
- **`FE-L3`** (design canvas review watch): any session that holds the Artifact tool; it edits nothing in the tree except `docs/design/canvas/` and its log.

### Session hygiene

Everything in the enterprise series' "Session hygiene" applies (pytest invocation, no bare `git stash`, the `/commit` skill, `.superpowers/sdd/progress.md`, no rewrite tournaments, `confidence-review` before done). Frontend additions:

- Run the frontend gates from `caos/frontend` in this order: `npm run lint`, `npx tsc --noEmit`, `npm run test:unit`, `npm run build`, then against the combined app `npm run test:workbench` and `npm run a11y`. Quote each summary line.
- `npm run build` writes `caos/frontend/out`, which the combined app serves; rebuild before every browser gate. Never delete build output to "optimize" it: the `noModule` polyfill bundle is expected (`CLAUDE.md`).
- The a11y script prints a literal combination count; adding or removing a route or viewport means updating the literal in the same commit, and the report says so.
- Keep a second table, `.superpowers/sdd/frontend/progress.md`, in the shape of `.superpowers/sdd/progress.md`, and write each task's report as `.superpowers/sdd/frontend/<prompt-id>-report.md` (assessments: `frontend-a0-code-audit.md`, `frontend-a1-ia-audit.md`, `frontend-a2-design-truth.md`; design briefs: `frontend-d1-directions.md`, `frontend-d2-screens.md`). The reports are the model's memory across compaction.
- Design canvases are proposals until you approve them. The approval is recorded in the design report and, for the IA, in a dated `DESIGN.md` addendum and a `docs/DECISIONS.md` §14 entry (`FE-G2` writes both); nothing in a canvas is authority before that.

### Decisions you must make after the assessments

Record each answer under `## Decisions` at the end of `.superpowers/sdd/frontend/frontend-a1-ia-audit.md`; `FE-D1` and `FE-G2` read them there. The recommendation is listed first.

- **D1 Target IA.** Adopt the 31 Aug production plan's eight destinations (Portfolio, Credit, Sources, Analysis, Market, Model, Report, Admin) and let `FE-A1` say exactly which current routes fold into which, with Run Console staying the one home for run progress and acceptance inside Analysis; or keep nine destinations and change only labels, kickers and titles; or take one of the alternatives `FE-A1` proposes. The first closes the seam the rail already opened.
- **D2 Route compatibility.** Keep every current slug as a static route that forwards to its new home with the query string intact (a static export cannot serve redirects, so each old route is a page that replaces history to the new one, and `workspaceAuthority.ts` treats the replay as a route replay); or cut the old slugs and accept that every retained link, smoke step and a11y route breaks at once. The first keeps deep links in retained evidence packages valid.
- **D3 Workspace.tsx.** Keep it one file and move only the code the IA change forces (the destination switch, the views that merge); or take the IA change as the moment to split the destination views into files while the authority machine and the reducer stay where they are. `CLAUDE.md` says do not decompose it casually; the IA change is the one non-casual moment. Behavior changes still go through the authority unit tests and the workbench smoke either way.
- **D4 Design tool path.** Use Claude Design's canvas inside Claude Code (`/design`) for directions and screens, retained as committed artboard files and exported PNG/PDF; or also stand up a claude.ai/design design-system project synced from the component library through `DesignSync` for the full product's editor; or take the Figma path (the Figma MCP is attached here) because your reviewers live in Figma. The first needs nothing beyond this session; the second needs a first-party claude.ai login, an org policy that permits Claude Design and the `/design-sync` skill enabled (it is not enabled in this session); the third adds a handoff format nobody in the repo consumes.
- **D5 Sequencing against enterprise Task 12.** Land `FE-G1` now and `FE-G2`/`FE-G3` before `ER-G8`, so the three-browser journey is parameterized once against the final routes; or land `ER-G8` first and let `FE-G2` rewrite its parameterized journey. `ER-G7` (Task 12a, backend) is independent and may run beside any of this.
- **D6 Approval record.** Record the approved canvas as a dated `DESIGN.md` addendum naming the artboards, their export digests and the canvas URL, plus one `docs/DECISIONS.md` §14 entry for the IA (destinations, route map, one-home rules), written by `FE-G2`; or keep the approval in the design report only. The first gives every later session one authority to read.

Every prompt below begins by pointing at the enterprise series' "Standing preamble" and at this addendum, so paste each prompt as written. The addendum is repository fact the preamble does not carry.

```text
FRONTEND ADDENDUM

# Design contracts
DESIGN.md and .impeccable.md govern the visual language; PRODUCT.md fixes the register (product, not brand) and the three personas with the buy-side credit analyst first; CONTEXT.md fixes the vocabulary and its "avoid" terms. # Structural rules from CLAUDE.md
Workspace.tsx is deliberately one file around the workspace-authority state machine (lib/workspaceAuthority.ts), which is the sole stale-response guard; behavior changes go through its unit tests and the workbench smoke. The frontend is a static export with trailing-slash routes (lib/workbench.ts#withQuery); dev proxies /api/* to :8000; production serves caos/frontend/out from the server image. The frontend never reads run-event payloads; event names trigger a RunRecord refetch. Every new server field is a named response model plus the pinned key sets in caos/tests/spec/test_http_contracts_spec.py; prefer a client-side change when the client can carry it.

Four unit tests readFileSync component source and assert literal strings (ModelBuilder.test.ts, ReportStudio.test.ts, workbench.test.ts, workspaceAuthority.test.ts); scripts/workbench-smoke.mjs pins the accessible name "Accept analytical snapshot", the "Evidence focus" heading at a two-ancestor depth, and a page.once("dialog") accept; scripts/a11y-axe.mjs hard-codes the route list, six desktop viewports and a literal combination count; workbench.test.ts pins the route table. Renaming any of these is allowed only in the same commit as the test change, and the report names each pair.

From caos/frontend: npm run lint, npx tsc --noEmit, npm run test:unit, npm run build; then against the combined app (python caos/server/dev.py with CAOS_PROVIDER=host_control and python caos/server/worker.py, or a second port with CAOS_URL set): npm run test:workbench and npm run a11y. Write .superpowers/sdd/frontend/<prompt-id>-report.md as you go and keep .superpowers/sdd/frontend/progress.md current, in the shape of the existing reports under .superpowers/sdd/.

Before every push, check that nobody else pushed to the branch since you fetched. ## How Claude Design fits the series

Claude Design is used here for the two decisions a code change cannot make well on its own: which information architecture to build, and what every destination and state looks like before code decides it. Three surfaces exist; D4 picks among them.

### The canvas inside Claude Code (`/design`) — the default

- **What it is.** The `/design` skill seeds Claude Design's component editor onto a multi-artboard canvas and publishes it as an Artifact. Every artboard is a self-contained `.dc.html` file; `canvas.json` lays them out, groups them into pages and picks the launch view; sticky-note annotations carry the motivation, the trade-off and the fence. In the browser you click to select, edit text in place, use the properties panel, undo, and **Save** publishes a new version for everyone with write access; readers get a read-only view plus PNG/PDF export. It is an early preview: the editor baked into a canvas does not update after publish, design-system tokens and the "request tweaks" loop are not in it, and two people saving at once means the second sees a conflict and a reload, so one reviewer at a time.
- **What it needs from the repository.** The skill matches an existing app from source by default: it lifts exact values from `globals.css` and the component markup (`WorkbenchShell.tsx`, `states.tsx`) rather than rounding to a grid. `FE-A2`'s truth sheet exists so that the match is verified rather than assumed, and so that the same numbers reach a human designer.
- **What the prompts make it produce.** `FE-D1` asks for two to four direction artboard sets with named motivations and trade-offs, static, low-fi, in the app's own tokens, and stops for your pick; `FE-D2` extends the same canvas with a "Screens" page of hi-fi artboards per destination and state, annotated with the served contract, the focus order and any pinned test string, and stops for your approval. Static mockups are the default; ask for a clickable prototype only where an interaction must be judged (the accept dialog, the drop zone), and say so in the brief.
- **Where the output lives.** The artboard working files are committed under `docs/design/canvas/<slug>/` (small text files; the seeded page is not committed), PNG exports with SHA-256 digests are retained under `.superpowers/sdd/frontend/design/`, and the approval is recorded in the design report and, for the IA, in the `DESIGN.md` addendum and the `docs/DECISIONS.md` §14 entry `FE-G2` writes. A canvas that someone edited in the browser is read back with the Artifact tool and re-extracted before any further change; `FE-L3` keeps the committed files equal to the saved canvas.
- **What it must not decide.** Tokens (they stay in `globals.css`), controls for unserved routes, the dark workspace rule, anything CONTEXT.md's vocabulary forbids, and authority: nothing on a canvas is binding until you say so.

### claude.ai/design with a synced design system — optional, after the direction is settled

If you want to iterate in the full Claude Design product, the `DesignSync` tool in this environment pushes a local component library into a claude.ai/design design-system project one component at a time (list and read, finalize a plan, then write), so that product designs with CAOS's real components. It needs a first-party claude.ai login, an organization policy that permits Claude Design, and the `/design-sync` skill, which is not enabled in this session; enable it before choosing this path. Use it for the screens page, never for the direction pick, and bring the result back the same way: working files committed, exports retained, approval recorded.

### Figma — only if a handoff format is required

The Figma MCP server is attached to this session (`generate_figma_design`, `use_figma`, `get_design_context` and the `/figma-*` skills it ships). It can push a running page or a `.dc.html` mockup into a Figma file and read a Figma frame back as design context. Nothing in the repository consumes Figma, so choose it only when reviewers outside this workflow need a Figma link, and keep the canvas as the record.

### The critique and audit passes

The repository's `impeccable` skill is the measuring instrument, not a design tool here: `audit` for the technical checks (accessibility, performance, responsive) in `FE-A0`, `document` and `extract` for the inventory draft in `FE-A2`, `craft` and `polish` for the implementation in `FE-G3`, and `critique` plus `audit` for the closing scores in `FE-G4`, written in the same shape as `IMPECCABLE-CRITIQUE-2026-08-31.md` so the two can be compared.

## How the Fable 5.1 guidance shaped these prompts

- **Goal and reason over steps.** Each prompt states the outcome, who it is for and what it enables, then binding constraints and a definition of done; the audit's commit plan and the canvas are referenced by file rather than restated as steps.
- **Assessment mode is explicit.** `FE-A0` to `FE-A2` say the deliverable is the assessment, so the model reports and stops instead of fixing; the fixes are a separate goal (`FE-G1`) that reads the report, which keeps repairs and the IA change on separate evidence.
- **Interactive design sessions are marked as such.** The design briefs override the autonomy block on purpose: the direction pick and the screen approval are the user's, so the prompts stop at those two points and say so, and ask at most one round of questions the brief leaves open.
- **Grounded progress.** Every pass claim needs the command and its output; the design prompts need the canvas URL, the export digests and the approval sentence in the user's words, so no later session can mistake a proposal for authority.
- **Load-bearing literals are named in the addendum**, because a rename that passes silently is the frontend's equivalent of a vacuous invariant test; each prompt requires the test change beside the code change in one commit.
- **A memory surface.** The reports under `.superpowers/sdd/frontend/` are written as the work proceeds and are what the next prompt reads; `FE-L3`'s log is what makes a canvas edited in the browser survive into the repository.
- **Loops on Opus** run fixed command sequences plus a diff against the last log entry, with the fences stated (edit nothing, never mark green what was not run, never force a republish, never change a token from a comment).
